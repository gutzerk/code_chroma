# Engine client & state (`web/src/{engine-client,state}/`)

- **`src/engine-client/`** — `EngineClient` interface is a **Facade** over the bridge API; its
  `subscribe(onChange)` method taps the bridge's live `WS /repos/{id}/events` channel. `HttpEngineClient`
  is the real HTTP+WebSocket implementation (opens one shared socket, reconnects on drop, fans out to
  every subscriber); `mockBridge.ts` is the fixture-backed stand-in the app uses by default. It has
  no live backend, so its `subscribe*` methods register on an in-memory `Map<EventType, Set<listener>>`
  bus instead: they only deliver a ping when a test drives the bus via the test-facing
  `emit(type, payload)`, so the ping→refetch layer stays visible in mock-backed specs.
  🔴 **A reopen resyncs**: every ping sent while the socket was down is gone, so on any reconnect
  after the first successful open `notifyResync()` nudges every bare-ping listener set once (skipping
  `-status`/`-output`/agent kinds, whose listeners expect payloads) — without this the canvas showed
  stale data forever after a bridge restart or laptop sleep. 🔴 Which is exactly why the reconnect
  **backs off**: `scheduleReconnect`'s delay starts at `RECONNECT_BASE_MS` (1s) and doubles to
  `RECONNECT_MAX_MS` (30s), because one synthetic `changed` fans out to the diff refresh, the C1
  review, the impact review, the canvas doc and one children fetch per expanded block — at the old
  flat 1s retry a socket that couldn't stay up replayed all of that every second, which reads on
  screen as an infinite loop. The base delay is earned back only by a connection that *lasted*
  (`socketOpenedAt` + `RECONNECT_STABLE_MS`), never by `onopen` alone: resetting on open would leave
  an open-then-instantly-drop socket retrying at 1s forever, i.e. the flap the backoff exists to damp.
  🔴 **Every request is cancellable; every *read* is also bounded.** The whole client funnels through
  exactly two `fetch()` calls — `fetchJson` and `fetchJsonOrNull` — and both pass
  `requestSignal(init, caller)`. 🔴 That helper applies `READ_TIMEOUT_MS` (30s) **only to a GET**
  (`isRead`: no `method`, or an explicit `"GET"`); a write carries the caller's signal alone, or no
  signal at all. Timing out a GET costs a retry, but timing out `acceptDiff`'s POST does not stop the
  commit the bridge is already making — it only stops us hearing the result, so the user would be
  told a commit failed that in fact landed. Where both a timeout and a caller signal apply they
  combine via `AbortSignal.any`, so whichever fires first aborts the real fetch.
  `getNode`/`getDiff`/`getChangeCards` take that optional `signal` (the Diff path is the one caller
  that can be called off mid-flight); every other read just gets the timeout. ⚠ `AbortSignal.any` and
  `AbortSignal.timeout` are both recent (Safari 17.4, Chrome 116) and there is no polyfill: missing
  either degrades to "no timeout" rather than throwing, since a slow read beats every request failing.
  `isAbortError(err)` is exported so a caller can stay quiet about a cancellation it asked for while
  still reporting real failures — `revealNode` and `refreshDiffs` both use it. This replaced a
  cancel-token pair in `useDiffToggle` that suppressed the *publish* while the request storm kept
  running; see [`web-canvas-shell.md`](web-canvas-shell.md). ⚠ Because a read's signal is
  unconditional, every `expect(fetch).toHaveBeenCalledWith(...)` assertion on a GET carries a `signal`
  now — a plain GET is no longer a single-argument `fetch(url)`.
  The interface has an optional
  `dispose()` (forwarded by `DelegatingEngineClient`): `EngineClientProvider`'s effect cleanup calls
  it on workspace switch, so a session no longer accumulates one abandoned socket per switch; it is
  non-terminal (StrictMode's double-mount relies on a later subscribe lazily reopening).
  `EventType` is **derived** from the kind unions (`DiagramEventKind`, `` `${SkillRunKind}-status` ``
  etc.), so the open-ended `` `custom/${typeId}` `` family type-checks with no casts. The FastAPI
  error decoder and JSON `RequestInit` helper live in `util/httpJson.ts`, shared with
  `agents/agentClient.ts`. A single `liveStore` version counter (`state/liveStore.ts`)
  is bumped per "changed" ping; `useNodeChildren` and `RootCanvas` re-fetch off it, reconciling in
  place (new nodes appear collapsed, gone nodes collapse out, open code/diff windows refresh without
  moving) so a live edit never resets the user's view or the camera.
  `fixtures.ts` is generated by `scripts/export_examples_fixture.py` (repo root) from a **plain
  filesystem walk over `examples/`** — folder/file nodes only, no symbol parsing, no LLM, and
  deliberately *not* real `GraphEngine.analyze()` output (it would flatten nested dirs like
  `examples/shadow-app/backend/routers/` the same way the engine's one-level-deep Pillar/Component
  grouping does). `web/README.md` claims otherwise and names a script
  (`export_shadow_app_fixture.py`) that doesn't exist — treat that doc as stale on this point.
  (`web/QUICKSTART.md` already names the real script correctly.)
  🔴 **The diagram seam is kind-keyed and epics rides it too**: `getDiagram<K extends
  DiagramFetchKind>(kind)` serves `c1`/`patterns`/`epics` off one `DiagramPayload` map
  (`DiagramFetchKind = DiagramKind | "epics"` in `state/types.ts` — epics shares the GET
  `/repos/{id}/{kind}` route shape and the layout pair, but is assembled from the requirements
  source, so it is NOT a `SkillRunKind` and has no generate/status/output trio). The old
  `getEpicsIndex()` is gone; only `getEpicsItem(itemId, expand?)` remains as its own method, because
  it takes params (a per-item detail fetch, not kind-shaped). `subscribeDiagram` takes
  `DiagramEventKind` (`SkillRunKind | DiagramFetchKind`); ⚠ "epics" sits in `EVENT_TYPES` even
  though the bridge never pushes that ping today — the listener-set map is keyed by it, and
  `subscribeDiagram("epics")` would crash on a missing entry otherwise (the index refetches off the
  shared "changed" ping). The skill-run trio is really a quartet now: each `SkillRunKind`'s
  `generateDiagram`/`getDiagramStatus`/`getDiagramOutput` and the epics-brief slice are joined by
  `cancelDiagram(kind)` and `cancelEpicBrief(itemId)` — the **Stop** affordance's backing calls
  (`POST /repos/{id}/{kind}/cancel` and `…/epics/{item_id}/brief/cancel`), which reset the job to
  idle and roll back a half-written artifact (see `graph-bridge-core.md`). Test stubs follow the
  seam: `DIAGRAM_STUB`/`diagramStub({c1, patterns, epics})` answer per kind, `EPICS_STUB` now carries
  only `getEpicsItem`, and the cancel methods live in `C1_CHANGES_STUB`/`EPIC_BRIEF_STUB` and are
  forwarded by `DelegatingEngineClient`.
- **`src/state/`** — `ExpansionStore` (`expansionState.ts`) is the single in-memory store for every
  block's expand/collapse state and the derived breadcrumb path. Never reflected in the URL; it *does*
  persist (the `persist()` write to `web/src/state/expansionPersistence.ts`) so a reload returns to
  the same open tree together with the saved camera (see `web-canvas-shell.md`). `createStore.ts` owns the store plumbing every store used to re-type by hand: a `Store` base
  class (one listener set, a `subscribe` shaped for `useSyncExternalStore`, protected `emit()`) that
  registers itself **workspace-scoped in its constructor** (its `reset()` is declared abstract, so a
  store that wants to be resettable must say how), and `resetWorkspaceStores()` (called from
  `App.tsx` when `useActiveWorkspace()` changes, skipping first render) resets every registered one
  so expansion/diff/plan/selection/trace state from one worktree never leaks onto another's canvas.
  Registration is now automatic — the opt-out is `markGlobalStore()`, chained at the export site for
  the few that must survive a switch: `agentStore` / `workspaceStore` / `branchStore` / `prStore`
  span every workspace (resetting `agentStore` would undo the very switch that triggered the reset),
  and `codeViewModeStore` and the panel-open stores (`terminalPanelStore`) are
  user chrome that survives a switch (`diagramWizardStore` was a member here too, before the
  diagram-management unification deleted it). `undoStore` is also marked global
  (its undo history should survive a diagram/workspace change). `collision/collisionStore`'s
  registry is not a `Store` at all — it follows component mount/unmount, so the reset set never
  touches it. `useDiagram`/`useDiagramGeneration` are the generic per-kind fetch+subscribe and
  job-status hooks; `EpicsView` now fetches its index via a dedicated `EpicsDiagramClient`
  (`engineClient.resolveEpicRef` for focused items, then `client.fetchItem`) instead of
  `useDiagram(engineClient, "epics", …)` (the hand-rolled `useEpicsIndex.ts` is deleted).
  `useAutoGenerate.ts`, the shared
  trigger-once-on-view-open generation effect C1 and Patterns used to share, is deleted too — every
  diagram/brief kind now generates only on an explicit click (Retry/Generate/Confirm), never as a
  side effect of opening a view.

- **Impact** — a slice of the hierarchy around a change (git diff) or plan (spec). Only the
  **skill-authored** diagram is drawn (`codechroma-draw-diagram`, impact type) — there is no
  deterministic slice preview. Impact renders through the one canvas document
  (`single-canvas.md`), not a bespoke view: `canvas/recipes.py::reshape` (the one shared
  server-side reshape every built-in type uses, 036) turns the authored `.codechroma/impact.json`
  into `CanvasNodeBox` elements with `render: "impact"` (`RecipeMenu`'s "Change impact" entry runs
  the recipe), and `useDiagramGeneration` + `useSkillOutput` drive
  the same Generate/Regenerate flow every diagram kind shares (`DiagramGeneratingPanel` while
  running, a stale banner → Regenerate when the diff/plan moved on). A read-only (PR) workspace
  hides the Generate/Regenerate actions — the backend refuses `POST .../impact/generate` there. The
  diff/plan source switch drives which slice a Generate gathers (`generateDiagram(kind, {source})` →
  `?source=` query). Boxes open the real Inspector on their `node_id`. `description`/`nodes[].style`
  (an **allow-listed** CSS subset via `authoredNodeStyle`, `canvas/authoredStyle.ts`) render the same
  way for every diagram kind now — `CanvasNodeBox` itself owns that, not an impact-specific
  component. Backend in `bridge/impact.py`, `impact_context.py`, `impact_resolver.py`,
  `diagrams/registry.py`; see `graph-bridge-core.md`. 🔴 The judgmental review sidecar (a per-box
  severity badge, driven by an agent-written `.codechroma/impact-review.json`) that used to sit on
  top of this was removed rather than kept half-wired (038 follow-up) — see `single-canvas.md`'s
  "Impact review" section and `graph-bridge-core.md` for what's gone.

Not yet built (still accurate): auto-grouping of large child sets, and search.

- **`src/agents/`** — the parallel-agent window layer; see [`parallel-agents.md`](parallel-agents.md) for the whole
  feature. In `web/` terms it is one more screen-space overlay (`AgentWindowLayer`), its own store
  (`agentStore`, planStore-shaped) and its own HTTP facade (`agentClient`, separate from
  `EngineClient` because `/agents` is not under `/repos/{id}`).
