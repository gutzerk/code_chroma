## Files

- Definition: `<repo>/.codechroma/workflows/<id>.json` = `{ id, name, inputs[], steps: [{ id, slug, kind: "agent"|"review", prompt, skill?, agent: "new"|"handoff"|"continue"|"continue:<stepId>", extraPrompt?, provider?, model?, pauseBefore, showDiff, showSummary, sendBackTo, input?: {name,label} }] }`. `input` (agent steps only) is the one value the run asks for at start; `{{name}}` is replaced in that step's prompt only. `inputs[]` at workflow level is kept for older files and is rewritten from the step inputs on save; `WorkflowDef.AllInputs()` (step inputs plus older ones) is what a run must be given. `prompt` is required for agent steps only; a review step may leave it empty. `pauseBefore` becomes a breakpoint when the run starts. `showDiff`/`showSummary` are review-step display flags. `sendBackTo` (an earlier agent step id) overrides which step "send back" reruns; otherwise the nearest earlier agent step.
- Step agent (`StepAgents` in `Models.cs`): `handoff` (a non-rerun agent step gets the nearest earlier non-skipped step's output tail, 4000 chars, and diff stat prepended), `new` (only its own prompt, never `--resume`), `continue`/`continue:<stepId>` (forks the source step's claude session: `--resume <sourceSession> --fork-session`, so the source session stays clean for a redo or a second continue; no handoff context; the record gets `resumedFrom` = the source step id). A continue never falls back to a fresh agent: when the source record has no `sessionId` (never ran, skipped) or the step's CLI no longer resolves to claude, the run stops with `✗ cannot continue <slug>: <reason>` in the step output and no process starts (`WorkflowRunner.PlanLaunch`). Older files with `context` load through `RunStore` as `previous`/missing -> `handoff`, `fresh` -> `new`, and `context` is never written back. `extraPrompt` is free text appended after the instructions (`

`), with `{{name}}` run inputs filled like the prompt. `provider`/`model` override the `workflow-step` call-site CLI (both null: the default): `SkillAgent.ResolveCli(provider, model)` resolves each step's CLI once (`CliResolver.ResolveProvider` for a provider, `CliResolver.WithModel` for a model-only override, which also rewrites a pinned `ANTHROPIC_MODEL`), the runner passes it as `RunOptions.Cli`, and that resolution, not the runner-wide agent, decides whether `--resume` is allowed. An unknown provider at run time fails the step like any launch error. Save-time checks live in `Workflows/WorkflowValidation.cs` (routes pass a provider-id -> adapter lookup): a continue needs an earlier agent step as source, the same provider as it, and a claude adapter; an unknown provider and agent settings on a review step are 400s. `StepRecord` also carries `usage {contextTokens,inputTokens,outputTokens,cacheReadTokens}` and `resumedFrom`. A rerun after Stop still resumes the step's own session (`--resume <id>`, no fork).
- Usage and chain length (019 Stage 2): when a step finishes (`Snapshot`), the runner reads its session's token usage with `Transcripts.ReadUsage(sessionId, worktree)` (`Agents/Transcripts.cs`, public static so terminal agents can reuse it): the `<sessionId>.jsonl` under `$CLAUDE_CONFIG_DIR/projects` or `~/.claude/projects`, last assistant entry that is not a sidechain, context = `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`; no transcript or no usage leaves `usage` as it was. The reader is injectable (`WorkflowRunner` ctor `usageReader`, like `sessionFinder`). `StepUsage` also carries `model` and `contextWindow` (`Agents/ModelSpecs.ContextWindow`: 1M for an id ending in `[1m]`, else 200k). Every run returned to callers (`View`/`Decorate`) gets per step `chainLength` (`StepAgents.ChainLengths`, one forward pass over the definition: 1 unless it continues) and `chainWarning` (`WorkflowLimits.ChainWarning`: a chain past 3 steps, or context past 60% of the window); both are recomputed on read, so stored values are never trusted, and the web shows `chainWarning` as is (it falls back to "past 3 steps" only for a record the bridge has not judged). Thresholds are constants in `Workflows/WorkflowLimits.cs` (the C# bridge has no config file). Whether a CLI can resume a session, and the argv for it, is `ICliAdapter.CanResume`/`ResumeArgs` (`CliAdapters.CanResume(adapterKey)`); save-time validation, the runner and redo all ask that instead of comparing against "claude".
- Run record: `<repo>/.codechroma/runs/<runId>.json` = `Run { id, workflowId, state, currentStepId, stopAfter, attempt, attempts[{n,branch}], breakpoints[], steps[StepRecord] }`, `StepRecord { stepId, attempt, status, output, diffStat, checkpointRef, sessionId }`. camelCase, written atomically by `RunStore`.
- Code: `dotnet/CodeChroma.Bridge/Workflows/` (`RunStateMachine.cs` pure table, `Models.cs`, `RunStore.cs`, `WorkflowRunner.cs`), `Routes/WorkflowRoutes.cs` (also holds `WorkflowRunners`, one runner per workspace).

## Behaviour

- States: running, paused, stopping, held, stopped, needs_you, done. `RunStateMachine.TryApply(state, command)` is the only transition table; an illegal pair returns null (`Apply` returns the state unchanged, the runner answers 409).
- Each run gets its own worktree (`WorktreeOps.WorktreePath(repo, "wf-<runId>")`, branch `workflow/<runId>`). Steps run sequentially through the `workflow-step` `SkillAgent` kind (registered in `SkillAgents`), keyed by run id, with the worktree as cwd; the `workflow-step` spec is `SkillAgentSpec.NoArtifact(...)` (null `Artifact`/`Validate`/`InvalidError`: nothing is snapshotted or restored, so no step failure or cancel rolls the code back) and a step counts as completed on exit code 0 alone. Only the chat agent has a scratch marker file in the temp dir (`WorkflowRunner.Marker("chat", key)`, key sanitized with `Path.GetInvalidFileNameChars` plus backslash), pre-written by `AskAgent`.
- Checkpoint: before an agent step starts, `git add -A` + an empty-allowed commit in the worktree; the sha goes in `checkpointRef`. After a step the session id (`Transcripts.FindSessionId`) and `git diff --shortstat` land in the record.
- Pause: `PauseGate` is awaited by `SkillAgent.ReadEvents` after each stream line is read and before it is parsed or queued, and by the flush loop before every flush (`RunOptions.PauseGate`, defaulting to a completed-task gate so the reader and flush loop just `await gate(token)`; `PauseGate.WaitAsync` reads its state lock-free). `Pause` flips run and step status to paused at once; from then on no output is flushed or written to the run record, and a line that arrives meanwhile is held (not lost, not duplicated) until resume. The gate wait honors the cancellation token and `Stop` opens the gate, so Stop while paused reaps the process promptly. Limit: pause is soft, the process is not suspended. A silent CLI (long tool call) keeps running and may even exit and change the worktree while paused; only its output and the step completion are held, and the CLI blocks once its stdout pipe fills. Between steps the loop waits on the same gate.
- Stop now: cancels the step process (`SkillAgent.Stop`), leaves the partial diff uncommitted in the worktree, step and run become stopped. Resume goes through `resume-from` the current step: reuses its record and checkpoint and, when a session id was saved, relaunches with `--resume <id>` (`RunOptions.ExtraArgs` on `Start`, passed into the CLI adapter's `BuildArgv`, which places them before a trailing positional prompt such as codex's, else appends them), else a fresh agent.
- Stop after step: sets `stopAfter` to the current step id (state stays running); at step end the run becomes held on the next step (record `held`, `currentStepId` = next) and the flag clears. `keep-running` clears it earlier.
- Breakpoints: step ids on the run; settable only on `pending` steps; reaching one makes the run held before it starts. They are never cleared by resume.
- Review step: run becomes needs_you. `approve` continues (or finishes); `sendBack` (async since 019 Stage 3) picks `sendBackTo` or the nearest earlier agent step and reruns it through the same path as redo (`RerunFrom`, `RunCommand.SendBack`): a new attempt, the rejected work kept on `<runId>/attempt-<n>`, the worktree reset to the target's checkpoint, the note as the first output line (`--- sent back: ... ---`) and in the prompt, event `run.redo.started`. It then runs on to the review gate again.
- A failing step (non-zero exit, timeout) stops the run with `✗ <error>` appended to the step output (the contract has no failed state).
- A bridge restart turns persisted running/paused/stopping runs into stopped (`Recover`).

## Routes and events

Under `/repos/{id}`: `GET /workflows`, `POST /workflows` (create; 409 when the id exists), `PUT /workflows/{wfId}` (update; 400 id mismatch/invalid, 404, runs already loaded keep their copy), `DELETE /workflows/{wfId}` (`WorkflowRunner.DeleteWorkflow` then `RunStore.DeleteWorkflow`; 404 unknown, 409 while a run of it is running/paused/stopping/held/needs_you or on a read-only workspace; finished runs of it are kept), `GET /runs`, `GET /runs/{runId}`, `DELETE /runs/{runId}` (done/stopped only, else 409; removes record, worktree and branches, event `run.deleted`), `DELETE /runs?state=finished` (clears every done/stopped run, `{deleted:[ids]}`), `POST /runs/{runId}/restart` (done/stopped only: wipes worktree, branches, outputs and messages and runs the SAME run again from step 1 with its inputs, re-reading the stored definition), `POST /workflows/{wfId}/runs`, `POST /runs/{runId}/pause|resume|stop{mode}|keep-running|breakpoints{stepId,on}|resume-from{stepId}|review{decision,note}|message|redo|redo/cancel`. All POSTs return the Run; PR (read-only) workspaces get 409. Events go over the repo socket as `{ type: "run", runId, event }` (`run.paused|resumed|stopping|stopped|held|step|done|message|redo.proposed|redo.started`); clients re-fetch the run (`workflowStore` coalesces list refetches and refetches per run), except `run.deleted`, which the store applies locally via `removeRun(id)`; `deleteRun`/`clearFinished` also drop the deleted runs locally instead of refetching the list.

## Run agent, messages, redo (Stages 3-4)

Code: `Workflows/WorkflowRunner.Steer.cs` (partial of `WorkflowRunner`), `WorktreeOps.CreateBranch/ResetHard`, `RunStore.SaveWorkflow`, `SkillAgents` kind `workflow-chat`.

- `POST /runs/{id}/message {target, text}` -> `{reply, messageId}`. `target` is `run` (the run agent) or a step id / `@slug` (that step's agent). Each call is one headless `SkillAgent` job (`workflow-chat`, key `<runId>:run` or `<runId>:<stepId>`, cwd = the run worktree, read-only `--tools Read,Grep,Glob`); a second ask to a busy agent is 409. It never touches run state, the pause gate or the step process. User, agent and system messages are stored on `Run.messages` (event `run.message`).
- The step agent gets the step prompt, its output tail and (when known) `--resume <sessionId>`; it has no MCP. The run agent gets a digest of every step (status, diff stat, output tail) and a per-run MCP config.
- Per-run MCP: `POST /mcp/runs/{repoId}/{runId}` (JSON-RPC over HTTP: initialize, tools/list, tools/call, ping), bearer token generated per run handle in memory. The bridge address comes from `IServer` at call time (`WorkflowRunners.McpUrl`); no URL (server not listening) means no MCP args. Tools: `pause`, `stop {mode}`, `propose_redo {from, note}`. `propose_redo` only sets `Run.redoProposal = {from, card{reruns, keeps, setsAside, note}}` and emits `run.redo.proposed`; the agent has no redo or edit tool. Only the run target gets the MCP.
- `POST /runs/{id}/redo {from, note?, stepEdit?{prompt, saveToWorkflow}}` (legal from stopped, held, done; `RunCommand.Redo`; awaits the parked loop first): commits the worktree's leftovers, creates branch `<runId>/attempt-<n>` at that commit (not under `workflow/`, git cannot hold both `workflow/x` and `workflow/x/y`; a numeric suffix `-2`, `-3` is added when the name is taken and the actual name lands in `attempts[n].branch`), `git reset --hard` to `from`'s `checkpointRef` only after the branch exists (if the reset fails the branch is deleted again and the redo answers 500), then attempt n+1. `from` must be an agent step that already has a checkpoint (else 409).
- Attempt bookkeeping: the set-aside `attempts[n]` gets `branch` and a `steps[]` snapshot (additive, so the UI can show attempt 1 read-only); a new `attempts[n+1]` points at the live `workflow/<runId>`. Steps before `from` are kept (`fromAttempt` set to their original attempt, `attempt` moves to n+1, output and checkpoint unchanged); `from` and later get fresh pending records. The note is the first line of `from`'s output (`--- redo note: ... ---`) and, with a note, leads the rerun prompt (`RedoPrompt`). Which agent reruns it (`PlanRedo`, shared with send back): on a claude CLI, a non-continue step forks (`--resume <id> --fork-session`) the nearest earlier agent step on the same provider whose record has a session, since that session never saw the rejected work, and the record gets `resumedFrom`; a continue step forks its own source; no such session (or not claude) means a fresh agent in the step's own mode (handoff context included). The source session is never resumed without `--fork-session`. Breakpoints are untouched; `from` itself is bypassed once, later breakpoints still hold. `stepEdit` changes the step prompt: `saveToWorkflow` rewrites `workflows/<id>.json`, otherwise it lives in `Run.promptOverrides` (reapplied when a run is reloaded). Event `run.redo.started`.
- `POST /runs/{id}/redo/cancel` clears `redoProposal`; the state stays (stopped).

## Races and guards (review of PR 148)

- 🔴 **A steer command can land between the loop's gate/stop check and its lock.** `LoopAsync` therefore retries instead of throwing: `TryBegin` (start/park a step) and `CompleteStep` return "not running" when the state is no longer `running`, and the loop waits on the gate again (`Pause` closes it, `Stop` sets `StopRequested` and opens it, both under the same lock as the state change). A completed step is never recorded as stopped because of a pause.
- **Stopping a `held`/`needs_you` run** leaves that step `pending` (it never started), so `ResumeFrom` does not build the "interrupted attempt" prompt.
- **Redo** does its git work (`KeepAttempt`: commit, branch, reset) outside the runner-wide lock. `Handle.Busy` is set meanwhile and `Transition` refuses state changes with a 409, so nothing races the worktree reset.
- **Saving a step edit to the workflow** loads the stored definition and changes only that step; the in-memory definition also carries this run's temporary overrides of other steps and must not be written back.
- **Chat agents** (`Message`): one at a time per `runId:target` (`_chatBusy`, checked and claimed under the lock); every chat passes `--tools Read,Grep,Glob --strict-mcp-config` (`--tools` does not limit MCP tools, so ambient MCP servers must not load) plus `--mcp-config` for the run agent only; chat and `--resume` are claude-only (`IsClaude`), other CLIs get a 409.
- **Per-run MCP** (`HandleMcp`): an unknown run and a bad token both answer 401; non-string `method`/`mode`/`from`/`note` are tolerated (a non-string `mode` is a tool error, never a silent `now`).
- **Step timeout:** `SkillAgent` stops the run's timeout while the pause gate holds the reader and restarts it on release (a silent CLI that is paused is still timed out).
